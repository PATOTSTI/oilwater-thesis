# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Thesis project: **Intelligent Oil-Water Separation System**. An ESP32-controlled surface boat autonomously detects, navigates to, and cleans oil slicks on water using a YOLOv8 model that runs on aerial drone imagery.

Two top-level apps:

- [backend/](backend/) — FastAPI service (Python) that holds all system state in memory, runs YOLOv8 inference, computes GPS waypoints, and brokers commands between the frontend and the ESP32.
- [thesis-frontend/](thesis-frontend/) — Vite + React 19 dashboard (JavaScript, Tailwind, react-router, react-query, leaflet, recharts) that operators use to monitor and command the boat.

There is no database. The ESP32 polls the backend; the frontend polls the backend; both are HTTP only.

## Common Commands

### Backend (run from [backend/](backend/))

```bash
pip install -r requirements.txt
uvicorn main:app --host 0.0.0.0 --port 8000 --reload --workers 1
```

- **Always run with `--workers 1`.** State lives in a single in-process `AppState` instance ([backend/core/state.py](backend/core/state.py)); multiple workers each get their own copy and endpoints will return stale defaults. The startup banner in [backend/main.py](backend/main.py) re-states this warning.
- `--host 0.0.0.0` is required so the ESP32 on the LAN can reach the API.
- Swagger UI at `http://localhost:8000/docs`, ReDoc at `/redoc`, liveness at `/health`.
- The YOLOv8 weights file must exist at [backend/ml/best.pt](backend/ml/best.pt). If it is missing the server still starts, but `POST /detect` returns 503 until the file is added.

### Frontend (run from [thesis-frontend/](thesis-frontend/))

```bash
npm install
npm run dev       # Vite dev server
npm run build     # production build
npm run preview   # serve the build
npm run lint      # eslint .
```

The frontend hard-codes `baseURL: 'http://localhost:8000'` in [thesis-frontend/src/api/apiClient.js](thesis-frontend/src/api/apiClient.js) — change it there if the backend is on a different host.

There is no test suite in either app.

## Architecture

### Three-layer system

```
Frontend (React)  ──HTTP──▶  FastAPI backend  ◀──HTTP polling──  ESP32 boat
                              (in-memory state)
```

- The ESP32 calls `GET /command` every ~1 s to fetch its next order and `POST /status` every ~1 s with sensor readings (GPS, IMU, battery, oil-sensor, pump state).
- In `automatic` or `cleaning` mode the backend **recomputes** the command on every `GET /command` based on the latest reported GPS/heading versus the active target — there is no push channel.
- The frontend polls `GET /status` every 3 s via React Query in [thesis-frontend/src/context/AppContext.jsx](thesis-frontend/src/context/AppContext.jsx); other pages have their own hooks under [thesis-frontend/src/hooks/](thesis-frontend/src/hooks/).

### Response envelope (backend)

Every endpoint — success **and** error — returns the same shape:

```json
{ "success": true|false, "data": ..., "message": "...", "timestamp": "..." }
```

This is enforced by `make_response()` in [backend/core/response.py](backend/core/response.py) and by the global `HTTPException` / `RequestValidationError` / `Exception` handlers in [backend/main.py](backend/main.py). When adding endpoints, return through `make_response()` and raise `HTTPException` for errors — do not return bare dicts or `JSONResponse`, or the envelope shape will drift.

On the frontend, the axios response interceptor in [thesis-frontend/src/api/apiClient.js](thesis-frontend/src/api/apiClient.js) unwraps `response.data`, so callers receive the envelope directly (not the axios wrapper). Throwing for `!success` is the caller's responsibility (see `AppContext` for the pattern).

### State (backend)

Single source of truth: the `AppState` singleton in [backend/core/state.py](backend/core/state.py). Modules read/write via `app_state["key"]`. Key fields: `current_mode`, `current_command`, `device_gps`, `target_gps`, `home_gps`, `heading`, `battery_level`, `model` (the loaded YOLO instance), `status_history` (cap 100), `detection_history` (cap 500), `event_log` (cap 1000), `cleaning` (waypoint queue + progress).

All data is lost on restart. This is intentional for the thesis demo; do not introduce a database without a discussion.

### Operating modes & mode-driven command resolution

Modes: `manual`, `automatic`, `cleaning`, `standby`, `returning`. The mode determines who decides the command:

- `manual` — `POST /command` from the frontend wins (movement commands rejected in any other mode).
- `automatic` — backend runs `compute_navigation_command()` in [backend/core/utils.py](backend/core/utils.py) (±10° heading tolerance, 2 m arrival radius) on every `GET /command`.
- `cleaning` — backend walks the spiral waypoint queue generated by `generate_spiral_waypoints()`, advancing when the boat is within 2 m of a waypoint.
- `standby` — pump off, command `stop`.
- `returning` — auto-entered when `battery_level < 20%` inside the `POST /status` handler.

Two commands bypass the mode gate and are always accepted: `emergency_stop` and `return_home`.

### GPS pipeline (oil detection)

`POST /detect` accepts a nadir drone image + drone GPS/altitude/heading/FOV. The pipeline in [backend/routes/detection.py](backend/routes/detection.py) and [backend/ml/detector.py](backend/ml/detector.py):

1. YOLOv8 inference, filter to confidence ≥ 0.60.
2. For each detection compute the bbox-centre pixel, then GSD (m/pixel from altitude+FOV), then `pixel_to_gps()` which offsets the drone GPS by the rotated pixel offset.
3. Compute `area_sqm` from bbox dimensions × GSD².
4. Assign a UUID `detection_id`, append to `detection_history`, update `last_detection`.

The frontend can then call `POST /navigate` with `source="detection"` and that `detection_id` to send the boat to that slick.

### Frontend layout

[thesis-frontend/src/App.jsx](thesis-frontend/src/App.jsx) is the root: fixed `Sidebar` (collapsed 64 px), fixed `StatusBar` on top, `AlertBanner` below it, then `<Routes>` for the 8 pages under [thesis-frontend/src/pages/](thesis-frontend/src/pages/). Pages: Dashboard, MapControl, ManualControl, Detection, Cleaning, Battery, Sensors, Logs.

Theme is `dark` by default, persisted in `localStorage` under `aquadetect_theme`; `AppContext` toggles the `dark` class on `<html>` so Tailwind's `class` strategy lights up `dark:` variants globally.

Alerts (low battery, oil detected, device offline) are rebuilt from scratch on every poll inside `AppContext` — "always reappear" alerts come back within ~3 s of dismissal while the condition holds; the oil alert stays dismissed until `oil_detected` flips back to false (re-arming logic in [thesis-frontend/src/context/AppContext.jsx](thesis-frontend/src/context/AppContext.jsx)).

## When working in this repo

- Keep response envelopes consistent — add to `make_response()` paths, not ad-hoc JSON.
- Treat `AppState` as the single source of truth; do not add module-level mutable state in route files.
- Detailed API contract (every endpoint, request/response shapes, mode transition rules, spiral math, logging events) is in [backend/README.md](backend/README.md) — consult it before adding endpoints or changing request shapes.
- Frontend hook query keys must match the ones used elsewhere (e.g. `['deviceStatus']`) so mutations in `useCommand` / `useMode` / `useNavigation` correctly invalidate the polling query.
